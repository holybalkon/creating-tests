# Розпізнавання тестів із документів

Користувачка перетягує документ (DOCX, TXT, MD) у браузер. Бекенд розпаковує його
без втрати оформлення й ріже на частини. Далі **ти читаєш документ як уважна людина**,
розумієш, де кожне завдання, який у нього тип, що є текстом-джерелом, а що
правильною відповіддю, і переносиш завдання в структуру платформи.

## 1. Принципи

1. **Кожен документ — незнайомий.** Нічого не переноси з попередніх документів:
   ні спосіб позначення відповідей, ні нумерацію, ні типи. Усе виводь із самого
   документа. Приклади в цих правилах — ілюстрації, а не шаблон.
2. **Розпізнаєш ти, а не код.** Не пиши скриптів чи регулярних виразів, що
   визначають межі завдань, тип чи правильну відповідь. Утиліти в `server/cli.mjs`
   лише показують план, збирають і перевіряють результат.
3. **Нічого не губиться і нічого не вигадується.** Кожен змістовний фрагмент
   документа або входить у завдання, або явно позначений як службовий
   (`skipped`). Сумнів → `status: "NeedsReview"` з поясненням в `issues`.
   Не видаляй незрозумілий текст і не вигадуй відповідь, якої немає.
4. **Завдання ніколи не рветься.** Текст-джерело, формулювання, варіанти й
   відповідь одного завдання — завжди в одному елементі, навіть якщо в документі
   вони розкидані по двох частинах.

## 2. Що робити, коли користувачка пише «готово»

```
node server/cli.mjs queue              # які документи чекають
node server/cli.mjs start <jobId>      # одразу позначає «в роботі» + план частин
```

1. Виконай `start` **першим** — фронтенд одразу перестане показувати «в черзі».
2. Прочитай `chunks/001.txt` (а для коротких документів — усі частини) і напиши
   `pipeline/jobs/<jobId>/analysis.md` (розділ 3). Поки цього файлу немає,
   фронтенд показує етап «Аналіз структури».
3. Для кожної частини `chunks/NNN.txt` запиши `parts/NNN.json` (розділ 7).
   Завдання, що починається в кінці частини, дочитай у наступній і запиши в
   частину, де воно **почалося**.
4. Після кожних 2–3 частин: `node server/cli.mjs assemble <jobId>` — це чернетка.
   Прочитай звіт: непокриті фрагменти, помилки типів, перетини рядків. Виправ
   відповідні `parts/*.json`, поки звіт не стане чистим.
5. Коли всі частини розібрано: `node server/cli.mjs assemble <jobId> --final`.
   Результат одразу з'явиться в браузері. Якщо у звіті є проблеми, виправ part і
   повтори `--final`.
6. У чаті — короткий підсумок: скільки завдань, які типи, скільки на перевірку
   і чому.

**Великий документ / продовження після перерви.** Стан зберігається на диску.
Щоб продовжити: `start <jobId>` (✓ біля вже розібраних частин), перечитай
`analysis.md` і останній `parts/*.json`, далі бери першу частину без ✓.

## 3. Аналіз структури (`analysis.md`)

Перш ніж розбирати завдання, прочитай початок документа (і прогорни решту,
якщо структура змінюється) та запиши коротко:

- **Розділи/вкладки:** які заголовки ділять документ (назви тестів, років,
  сесій). Це мітки походження (`source`), а не завдання.
- **Нумерація:** як позначено початок завдання («Завдання 7», «7.», «№7», без
  номера); чи нумерація починається заново в кожному розділі.
- **Варіанти:** якими маркерами (А–Д, 1–4, a–d), в одному рядку з текстом чи
  окремо.
- **Правильна відповідь:** чим позначена (розділ 6). Перевір на 5–10 завданнях,
  чи позначка однозначна.
- **Тексти-джерела:** чи є уривки, «Текст А/Б», ситуації, мікротексти з
  пропусками; до яких завдань вони відносяться.
- **Легенда/службові позначки:** напр. «жовтим виділено те, що вже є на
  платформі» → як це відобразиш (`tags`).
- **Очікувана кількість завдань** за розділами — потім звір зі звітом збірки.

## 4. Як читати вхід

Рядки частин мають вигляд `L00042| <p>…</p>`. Номер `L…` — глобальний; саме
його вказуєш у `lines`.

- `<strong>`/`<b>` — жирний, `<em>`/`<i>` — курсив, `<u>` — підкреслення,
  `<s>` — закреслення, `<mark class="hl-yellow">` — підсвітка маркером (колір у
  класі), `<sub>/<sup>` — індекси, `<h1>…<h6>` — заголовки, `<table>` — таблиця.
- `<p> </p>` — порожній абзац, часто роздільник між завданнями.
- `<img src="assets/img-003.png">` — зображення; посилайся на нього як
  `{"src": "img-003.png"}`.
- TXT/MD — звичайний текст; оформлення там лише те, що видно символами.
- Колір шрифту з Word не зберігається. Якщо легенда документа спирається на колір
  шрифту, а в тексті його не видно — `NeedsReview` з поясненням.

## 5. Межі й тип завдання

**Одне завдання** = одне питання/умова, на яке учень дає відповідь, разом з усім,
без чого його не розв'язати (текст-джерело, таблиця, малюнок, варіанти).

Визначай тип так:

1. **Є кілька пропусків в одному тексті, і до кожного пропуску своя відповідь**
   (або свої варіанти) → `fill_in_blanks`.
   Якщо документ сам ділить такий текст на окремі нумеровані завдання («Завдання
   1… (1)___», «Завдання 2… (2)___») — зберігай поділ документа: кожне таке
   завдання — окреме `single_choice` з реченням-пропуском у `questionText`.
2. **Є окремий текст-джерело** (уривок, «Текст А/Б», стаття, ситуація), і **окреме
   питання** до нього → `reading_comprehension`. Текст іде в `contexts`, питання —
   у `questionText`. Якщо до одного тексту кілька питань — кожне окреме завдання з
   тим самим текстом (використай `sharedContexts`).
3. **Треба поєднати елементи двох списків** (1–4 ↔ А–Д, «встановіть
   відповідність») → `matching`.
4. **Варіанти, правильних кілька** → `multiple_choice`.
5. **Варіанти, правильний один** → `single_choice`.

Типові помилки, яких треба уникати:

- Речення з пропуском («Педагоги зауважують, що (4)____ мислення…») і варіанти до
  нього — це `questionText` + `options`, тип `single_choice`. **Не** `contexts`
  з порожнім `questionText`.
- «Текст А», «Текст Б», «Прочитайте…», «Ситуація № 2» — не завдання, а частина
  контексту до наступних питань.
- Заголовок розділу/вкладки, інструкція до групи («Завдання 1–18 мають чотири
  варіанти…»), легенда — не завдання: `skipped`.
- Номер завдання («Завдання 7», «7.») не входить у `questionText` — він іде в
  `originalNumber`.

## 6. Правильна відповідь

Визнач позначку на перших завданнях і застосовуй однаково:

- символи (✔, ✓, +, *, стрілка) біля варіанта;
- ключ: «Відповідь: Б», «Правильна: 3», таблиця відповідей наприкінці документа;
- оформлення: жирний, підкреслення, підсвітка, курсив тексту варіанта.

Порівнюй відносно: якщо **всі** літери-маркери жирні, це просто оформлення, а
правильний — варіант, у якого жирний **текст** (у тому числі коли маркер і текст
у різних рядках: `<strong>Б</strong>` / `<strong>мінливим</strong>`).

У результат клади **чистий текст** варіанта: без маркера, без символу-позначки,
без тегів. Факт правильності — тільки `isCorrect: true`. Якщо позначка
неоднозначна або її немає — не вгадуй: `NeedsReview` і опис в `issues`.

Не переноси в текст завдання оформлення, яке видає відповідь (жирне слово-відповідь
у реченні тощо).

## 7. Формат `parts/NNN.json`

```json
{
  "chunk": 1,
  "sectionTitle": "Назва документа або першого тесту (лише в першій частині)",
  "skipped": [
    { "lines": [1, 1], "kind": "legend", "reason": "легенда: жовтим — вже на платформі" },
    { "lines": [2, 2], "kind": "tab", "title": "Демонстраційний тест 2024" },
    { "lines": [40, 41], "kind": "instruction", "reason": "інструкція до завдань 1–18" }
  ],
  "sharedContexts": [
    { "id": "t11", "label": "Текст А", "lines": [120, 128] },
    { "id": "t11b", "label": "Текст Б", "lines": [130, 137] }
  ],
  "questions": [
    {
      "lines": [3, 8],
      "originalNumber": 1,
      "type": "single_choice",
      "questionText": "Нобелівську премію … робить індивідуальне існування (1)________.",
      "options": [
        { "marker": "А", "text": "банальним", "isCorrect": false },
        { "marker": "Б", "text": "екзальтованим", "isCorrect": false },
        { "marker": "В", "text": "універсальним", "isCorrect": true },
        { "marker": "Г", "text": "ірреальним", "isCorrect": false }
      ]
    }
  ]
}
```

Поля завдання:

| Поле | Що це | Коли |
|---|---|---|
| `lines` | `[перший, останній]` рядок самого завдання (номер, умова, варіанти) | завжди |
| `contextLines` | рядки тексту-джерела, якщо не через `sharedContexts` | за потреби |
| `type` | один із 5 типів | завжди |
| `originalNumber` | номер у документі | якщо є |
| `source` | розділ/вкладка; можна не писати — підставиться з `skipped` kind `tab` | — |
| `tags` | позначки з легенди | якщо є |
| `contexts` | `[{label?, lines}]` — текст візьметься з документа дослівно; або `[{label?, content}]`; або `{"ref": "t11"}` | текст-джерело |
| `contextRefs` | `["t11", "t11b"]` — коротший запис посилань на `sharedContexts` | спільні тексти |
| `questionText` | формулювання; можна `<strong>`, `<em>`, `<u>`, `<sub>`, `<sup>`, `<br>` | завжди, крім `fill_in_blanks` без окремої умови |
| `images` | `[{"src": "img-003.png", "alt": "…"}]` | малюнок у завданні |
| `options` | `[{marker, text, isCorrect, image?}]` | single / multiple / reading |
| `correctAnswer` | текстова відповідь без варіантів | reading без варіантів |
| `blankText` | текст, де кожен пропуск замінено на `{{1}}`, `{{2}}` | fill_in_blanks |
| `blanks` | `[{index, answer}]` або `[{index, options:[…]}]`, `acceptable?` | fill_in_blanks |
| `pairs` | `[{left, right}]` — правильні відповідності | matching |
| `distractors` | зайві варіанти правої колонки | matching |
| `explanation` | пояснення з документа | якщо є |
| `status`, `issues` | `NeedsReview` + причина, якщо сумніваєшся | за потреби |

Не пиши `number`, `correctMarkers`, `rawText`, лічильники — їх рахує збірка.

Приклади інших типів:

```json
{ "lines": [300, 312], "originalNumber": 11, "type": "reading_comprehension",
  "contextRefs": ["t11", "t11b"],
  "questionText": "Авторка тексту А наводить розлогий перелік ознак Homo Sovieticus передусім для того, щоб",
  "options": [ { "marker": "А", "text": "підтвердити думку, що патерналізм невикорінюваний", "isCorrect": false },
               { "marker": "Б", "text": "показати, що патерналізм складне соціальне явище", "isCorrect": true },
               { "marker": "В", "text": "переконати, що українцям притаманні всі ці ознаки", "isCorrect": false },
               { "marker": "Г", "text": "інформувати про найбільш авторитетний перелік ознак", "isCorrect": false } ] }

{ "lines": [500, 520], "type": "fill_in_blanks",
  "questionText": "Виберіть правильний варіант для кожного пропуску.",
  "blankText": "Учені {{1}} гіпотезу, яку згодом {{2}}.",
  "blanks": [ { "index": 1, "options": [ { "marker": "А", "text": "висунули", "isCorrect": true },
                                          { "marker": "Б", "text": "виставили", "isCorrect": false } ] },
              { "index": 2, "answer": "підтвердили" } ] }

{ "lines": [600, 612], "type": "matching",
  "questionText": "Установіть відповідність між автором і твором.",
  "pairs": [ { "left": "Т. Шевченко", "right": "«Кобзар»" }, { "left": "І. Франко", "right": "«Захар Беркут»" } ],
  "distractors": ["«Енеїда»"] }
```

## 8. Самоперевірка перед записом частини

- Кожне завдання має непорожнє формулювання і правильну кількість правильних
  відповідей для свого типу.
- Тексти варіантів без маркерів, позначок і тегів.
- Текст-джерело не загубився і не опинився замість формулювання.
- Кожен змістовний рядок частини або в `lines`/`contexts` завдання, або в `skipped`.
  `skipped` — лише для того, що точно службове (заголовок, інструкція, легенда,
  мітка «Текст А»). Незрозумілий фрагмент туди не клади: залиш його непокритим —
  фінальна збірка сама винесе його в «Потребує уваги».
- Зображення з фрагмента прикріплені до завдання чи варіанта.
- Звіт `assemble` після частини — без нових помилок, або вони свідомо
  залишені як `NeedsReview` з поясненням.
